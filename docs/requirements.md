# فاز ۱ — تحلیل نیازمندی‌ها

## 1. هدف پروژه

ساخت یک وب‌اپ ساده، قابل توسعه و کاربرپسند برای مدیریت کارها (Task Management) که کاربر بتواند کارهای خود را ثبت، مشاهده، ویرایش، حذف و پیگیری کند.

نسخه اول باید ساده باشد و از ایجاد پیچیدگی‌های غیرضروری جلوگیری کند؛ معماری باید طوری انتخاب شود که در فازهای بعدی امکان افزودن احراز هویت، چندکاربره‌بودن، اعلان‌ها و گزارش‌گیری وجود داشته باشد.

## 2. محدوده نسخه اولیه (MVP)

### مدیریت کارها
- ایجاد کار جدید
- مشاهده فهرست کارها
- مشاهده جزئیات یک کار
- ویرایش کار
- حذف کار
- تغییر وضعیت کار
- تعیین اولویت
- تعیین تاریخ سررسید
- افزودن توضیحات

### وضعیت‌ها
- انجام‌نشده (`todo`)
- در حال انجام (`in_progress`)
- انجام‌شده (`done`)

### اولویت‌ها
- کم (`low`)
- متوسط (`medium`)
- زیاد (`high`)

### جست‌وجو و فیلتر
- جست‌وجو بر اساس عنوان
- فیلتر بر اساس وضعیت
- فیلتر بر اساس اولویت
- مرتب‌سازی بر اساس تاریخ ایجاد یا سررسید

## 3. موجودیت اصلی سیستم

### Task

| فیلد | نوع پیشنهادی | الزامی | توضیح |
|---|---|---:|---|
| id | UUID/ID | بله | شناسه یکتا |
| title | string | بله | عنوان کار |
| description | text | خیر | توضیحات |
| status | enum | بله | وضعیت کار |
| priority | enum | بله | اولویت |
| due_date | datetime/date | خیر | تاریخ سررسید |
| created_at | datetime | بله | زمان ایجاد |
| updated_at | datetime | بله | زمان آخرین تغییر |

## 4. نیازمندی‌های عملکردی

1. کاربر باید بتواند یک Task جدید ایجاد کند.
2. سیستم باید Taskهای موجود را نمایش دهد.
3. کاربر باید بتواند اطلاعات Task را ویرایش کند.
4. کاربر باید بتواند Task را حذف کند و سیستم باید برای حذف از کاربر تأیید بگیرد.
5. کاربر باید بتواند وضعیت Task را تغییر دهد.
6. کاربر باید بتواند اولویت Task را تعیین یا تغییر دهد.
7. کاربر باید بتواند برای Task تاریخ سررسید تعیین کند.
8. سیستم باید امکان جست‌وجو و فیلتر Taskها را فراهم کند.
9. سیستم باید تاریخ ایجاد و آخرین تغییر هر Task را نگهداری کند.

## 5. نیازمندی‌های غیرعملکردی

- رابط کاربری ساده و قابل فهم باشد.
- طراحی Responsive باشد.
- ساختار پروژه قابل توسعه باشد.
- منطق کسب‌وکار از رابط کاربری جدا باشد.
- داده‌ها در یک لایه مشخص مدیریت شوند تا در آینده تغییر پایگاه داده ساده باشد.
- خطاهای ورودی کاربر به‌صورت قابل فهم نمایش داده شوند.
- عملیات حذف و تغییرات مهم با کنترل مناسب انجام شوند.
- کد از ابتدا برای تست‌پذیری مناسب سازمان‌دهی شود.

## 6. نقش‌ها و کاربران

در MVP اولیه فقط یک کاربر/مالک سیستم در نظر گرفته می‌شود و احراز هویت در این فاز پیاده‌سازی نمی‌شود.

در طراحی باید امکان اضافه‌شدن User در فازهای بعدی در نظر گرفته شود؛ به‌خصوص اتصال Task به صاحب آن.

## 7. جریان‌های اصلی کاربر

### ایجاد Task

`Dashboard → ایجاد Task → تکمیل فرم → اعتبارسنجی → ذخیره → نمایش Task در فهرست`

### ویرایش Task

`فهرست Taskها → انتخاب Task → ویرایش → اعتبارسنجی → ذخیره → نمایش نتیجه`

### تغییر وضعیت

`فهرست/جزئیات Task → تغییر وضعیت → ذخیره → به‌روزرسانی UI`

### حذف Task

`فهرست Taskها → حذف → تأیید کاربر → حذف از داده‌ها → به‌روزرسانی فهرست`

## 8. صفحات موردنیاز MVP

1. **Dashboard / Tasks** — صفحه اصلی و فهرست Taskها
2. **Create Task** — فرم ایجاد Task
3. **Edit Task** — فرم ویرایش Task
4. **Task Details** — جزئیات Task

در صورت امکان، Create و Edit می‌توانند در یک فرم مشترک پیاده‌سازی شوند.

## 9. API پیشنهادی

اگر در فاز معماری Backend جداگانه انتخاب شود، API اولیه می‌تواند شامل این endpointها باشد:

- `GET /api/tasks`
- `GET /api/tasks/:id`
- `POST /api/tasks`
- `PUT /api/tasks/:id`
- `DELETE /api/tasks/:id`

فیلتر و جست‌وجو در `GET /api/tasks` از طریق query parameter انجام شود.

## 10. قواعد اعتبارسنجی اولیه

- عنوان Task نباید خالی باشد.
- عنوان باید طول معقول داشته باشد.
- status فقط یکی از مقادیر تعریف‌شده باشد.
- priority فقط یکی از مقادیر تعریف‌شده باشد.
- due_date در صورت وجود باید مقدار معتبر تاریخ باشد.
- فیلدهای غیرقابل اعتماد از سمت Client نباید بدون اعتبارسنجی وارد لایه داده شوند.

## 11. موارد خارج از محدوده MVP

فعلاً این موارد ساخته نمی‌شوند:

- ثبت‌نام و ورود کاربران
- نقش‌های مختلف کاربران
- اشتراک‌گذاری Task
- اعلان Push/Email
- فایل و پیوست
- تقویم پیشرفته
- گزارش‌گیری پیچیده
- همکاری هم‌زمان چند کاربر
- پرداخت و اشتراک

این موارد برای فازهای بعدی قابل بررسی هستند.

## 12. معیار پذیرش MVP

MVP زمانی قابل قبول است که کاربر بتواند بدون خطای جدی:

- یک Task ایجاد کند؛
- Taskها را ببیند؛
- Task را ویرایش کند؛
- وضعیت و اولویت را تغییر دهد؛
- Task را حذف کند؛
- Taskها را جست‌وجو و فیلتر کند؛
- و اطلاعات پس از Refresh از بین نرود.

## 13. تصمیمات فاز ۱

- پروژه از ابتدا با رویکرد MVP توسعه داده می‌شود.
- در فاز ۱ کدنویسی محصول انجام نمی‌شود؛ این سند مبنای فاز معماری و پیاده‌سازی است.
- انتخاب دقیق Stack تکنولوژی در فاز معماری انجام می‌شود و نباید بدون بررسی نیازهای توسعه تحمیل شود.
- معماری باید امکان افزودن Authentication و User ownership را در آینده حفظ کند.
